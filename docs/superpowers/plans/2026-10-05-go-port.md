# athens-transit-rt Go port — Implementation Plan

> **For agentic workers:** executed inline (no subagents unless Harold asks). Steps use checkbox syntax.

**Goal:** Port foivospro/athens-gtfs-realtime (SHA `1ae9338`) to one Go binary that serves the
contract in `docs/CONTRACT.md` for the whole OASA network from the Oracle VPS, plus a GitHub
Actions pipeline that preprocesses the static GTFS.

**Architecture:** Heavy GTFS parsing runs in GitHub Actions (`atrt snapshot`), which writes a
compact gzip+gob snapshot (release asset) and the static map JSON (GitHub Pages). The VPS
process (`atrt serve`) downloads the snapshot, polls OASA telematics under one global paced
budget with priority tiers, matches vehicles to trips (memory matcher = Hungarian + history),
and serves `/v1/*` JSON and GTFS-RT feeds behind Cloudflare.

**Tech stack:** Go 1.26, stdlib `net/http`, `google.golang.org/protobuf` +
`github.com/MobilityData/gtfs-realtime-bindings/golang/gtfs` (v1.0.0, proto2 pointer fields),
`modernc.org/sqlite` (driver name `sqlite`, pure Go), `time/tzdata` embedded.

## Facts verified before planning

- GTFS (data.gov.gr, ETag `"0x8DEDCCA8D64FB3B"`, Last-Modified 2026-07-08): 486 routes rows,
  97,217 trips, 4.24 M stop_times (225 MB), 65,709 shape points, 515 shapes, 8,040 stops,
  calendar `day_1..day_7` valid **20260706–20261006** (expires tomorrow), route_type 3 (bus)
  or 11 (trolley). Data.gov.gr answers HEAD with a 302 to Azure blob; ETag/Last-Modified/size
  live on the final response (must follow redirects).
- Telematics: `webGetLines` = 473 rows `{LineCode, LineID, LineDescr, LineDescrEng}`; one
  LineID can have several LineCodes (Α1: 1566, 962; Χ96: 892, 1153). `webGetRoutes&p1=938` →
  3922/3923/3924. `getBusLocation` rows `{VEH_NO, CS_DATE "Oct  5 2026 11:10:38:000AM", CS_LAT,
  CS_LNG, ROUTE_CODE, VEH_HEADING}` (all strings). `getStopArrivals` → `{route_code, veh_code,
  btime2}`.
- GTFS route_short_name == telematics LineID (upstream relies on this).
- Upstream live loop uses the greedy `Matcher`; `HungarianMatcher` and `MemoryMatcher` exist for
  `replay`. Port all three; live default = `memory` (flag `--matcher`). Documented deviation.

## Key design decisions

1. **Compact model.** Trips share stop *patterns* (stop ids + stop_sequence) and *time
   profiles* (arrival/departure offsets from trip start, `uint16` seconds, departure stored only
   when ≠ arrival). A trip = `{ID string, Route, Service, Shape, Dir int8, Headsign, Pattern int32,
   Profile int32, Start int32}`. Dedup by hash. Expect < 30 MB heap for the whole network.
2. **Snapshot** = gzip(gob(`snapshotV1`)) with a `Version` field, GTFS ETag/Last-Modified, build
   time. Manifest `manifest.json` `{gtfs_version, etag, last_modified, sha256, size, built_at}`.
   Both are assets of one rolling release tag `gtfs-snapshot` (upload snapshot first, manifest
   last, `--clobber`). VPS polls the manifest URL every 30 min with `If-None-Match`; on new
   sha256 it downloads, verifies sha256, decodes, swaps atomically, keeps the file in the state dir.
3. **gtfs_version** = date of the zip's Last-Modified header, `YYYY-MM-DD` (`2026-07-08`);
   fallback max(calendar start_date) when the header is missing. `gtfs_expires` = max calendar end_date.
4. **Variant** = GTFS `shape_id`. Live `variant` = matched trip's shape; unmatched → the mapped
   shape with the most trips for that route code; null if none.
5. **Telematics metadata** (`LineID → LineCodes → RouteCodes`, ~500 requests) cached in
   `$STATE/telematics-meta.json`; refreshed every 24 h at lowest priority; first boot without a
   cache fetches it before polling (≈2 min at 4 rps). `webGetStops` for RouteMapper is fetched
   lazily per unmapped route code and cached in the same file.
6. **Rate limit.** One dispatcher goroutine starts at most one request every `1/rps × backoff`
   seconds (evenly spaced, no bursts), max 8 in flight. Backoff: on error / HTTP ≥ 500 / 429 /
   latency > 5 s → multiplier ×2 (cap 8); each fast success → ×0.9 (floor 1). `rps` default 4,
   clamped to (0, 5].
7. **Scheduling.** Unit of work = one line poll = its *active* route codes, issued back to back,
   then match + publish. Tiers per line: watched (requested in last 10 min) 30 s; dense (≥ 5
   fresh vehicles last poll) 60 s; other active 150 s (allowed range 120–300 s); inactive (no
   candidate trip in [start−15 min, end+60 min] today/yesterday) not polled. A route with no
   vehicles in its last 2 polls is polled at most every 300 s unless watched. Budget allocation:
   demand of tier = Σ routes/interval; watched get min(demand, 0.5·rps); dense then other share
   the remainder; a tier over budget has its intervals stretched by demand/allowance. Next job =
   earliest due. `next_update_at` = due time + routes/rps + 2 s.
8. **Cache-Control** for `/v1/lines/{id}` = `public, max-age=clamp(next_update_at − now, 5, 300)`;
   inactive line → `{vehicles: [], updated_at: now, next_update_at: now+300}`; active never
   polled → 503 `warming_up` (`max-age=5`); unknown → 404 (`max-age=300`).
9. **Line ids**: trim, `strings.ToUpper`, Latin→Greek map `ABEZHIKMNOPTYX → ΑΒΕΖΗΙΚΜΝΟΡΤΥΧ`.
   Known = GTFS short names ∪ telematics LineIDs.
10. **Matching state** is per line; a snapshot swap rebuilds matchers. MemoryMatcher’s position
    cache is pruned to fixes within `HISTORY_S` (upstream grows unbounded).
11. **Static site**: `lines.json` from GTFS (name = route_long_name of the line’s route with most
    trips; name_en from one `webGetLines` call in the Action, `""` on failure; color
    `#`+route_color; kind trolley if route_type 11). `lines/{id}.json` variants per shape_id
    (headsign = most common trip_headsign, direction = direction_id, shape rounded to 5 dp,
    stops = most common pattern). Deployed with `actions/deploy-pages`.
12. **Tools**: `record`/`compare`/`replay` run on a dev machine (not the VPS), default 1 rps,
    accept `--gtfs zip` or `--snapshot file`. `record` keeps upstream’s SQLite schema so upstream
    recordings replay unchanged.

### Task 1: gtfs model + zip loader + calendar
Tests (synthetic zip built in test from strings): stop_times out of order → sorted by
stop_sequence; `24:35:00` parsed as 88,500 s; trips with < 2 stop_times dropped; patterns and
profiles deduplicated (two trips same stops, different start → 1 pattern, 1 profile);
`ServiceActive` honours calendar_dates type 1/2 over weekday; `FeedEnd`; `CandidateTrips` returns
yesterday’s trip at 00:20 when it ends 24:40; BOM in header handled.

### Task 2: snapshot encode/decode + manifest
Round-trip test equality; corrupted gzip → error; version mismatch → error; sha256 in manifest.

### Task 3: telematics client
`ParseCSDate` table test (AM/PM, 12 AM → 0 h, double space); empty/`""`/`null` body → empty;
`{"error":..}` → error; httptest server; limiter test with fake clock: 4 rps → starts 250 ms
apart; error → interval doubles; recover ×0.9; clamp rps to 5.

### Task 4: geo
Port `Polyline.candidates` (loop route gives 2 candidates), `snapStops` Viterbi (monotonic
order; returns nil when a stop > 150 m), `Progress`. Golden tests computed with upstream Python on
the same inputs (run the Python functions via a small script; numpy not needed for these).

### Task 5: LSA
Port scipy rectangular LSAP (augmenting shortest path with dual potentials, rows ≤ cols by
transposing). Tests: brute force over all permutations for random 1..6 × 1..8 matrices (1000
cases) equal minimal cost; infeasible handling via large costs; known scipy example
`[[4,1,3],[2,0,5],[3,2,2]]` → rows [0 1 2] cols [1 0 2], cost 5.

### Task 6: matcher (greedy, Hungarian, memory) + RouteMapper
Port 1:1 with constants. Tests on synthetic straight-line route: on-time vehicle gets delay ≈ 0;
vehicle 120 s late gets delay 120; waiting at terminal → waiting, delay 0; two vehicles / two trips
→ Hungarian avoids the greedy steal case (craft costs where greedy is worse); sticky keeps
previous trip under small ambiguity; memory anchors at departure; delay outside [−600, 3600] →
unmatched. RouteMapper: equal code → itself; else similarity ≥ 0.6 with fake stops fetcher.
Integration test on real line 040 fixture (recorded busloc + trimmed GTFS subset in testdata):
every vehicle gets a trip, delays within ±60 min.

### Task 7: feed builder
Header timestamp = max(now, newest fix); unmatched vehicle has only route_id; waiting →
STOPPED_AT + departure delay; entity ids `vehicle-{id}`, `trip-{trip}-{YYYYMMDD}`. Round-trip
unmarshal test; JSON via protojson.

### Task 8: scheduler
Pure functions tested: `Classify` (watched/dense/other/inactive), `Allocate(budget, demands)`
(watched capped at 50 %, stretch factors), empty-route slowdown, `NextDue` ordering, and
`NextUpdateAt`. Loop test with fake telematics + fake clock: total request rate never exceeds rps
over any 10 s window.

## Risks
- The GTFS expires 2026-10-06. If OASA does not publish a new one, no trip matches after that
  date; vehicles still appear (positions + route). Status `ok` stays true for positions but the
  frontend banner uses `gtfs_expires`.
- OASA metadata bootstrap (~500 requests) at first boot; cached afterwards.
- Pages for a repo without a `gh-pages` branch must be enabled with `build_type=workflow`.
